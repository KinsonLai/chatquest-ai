# ChatQuest AI 0.3.1

Recoverable server errors now tell the chat client what to do next, instead of leaving the player to type another prompt.

- `retryable:true` includes a one-retry limit and an explicit next recovery call for turn commits and checkpoint restores. Other operations retry the identical request using their own idempotency rules; branch keys are separate from turn receipts. Recovery reads do not recursively request themselves.
- If recovery finds a committed receipt, return that saved result without another submission. Otherwise preserve the exact original tool, arguments and idempotency key on retry.
- Game validation, known permanent storage errors and permission denials are not instructions to resend unchanged input.
- The budget is one automatic retry per original operation. Stop if recovery or that retry fails; do not loop.

This is machine-readable and natural-language advice for the client model. The server does not run a background retry or override client approvals. A ChatGPT safety block before dispatch cannot receive this response. SDK-level argument validation may also occur before the application error handler.

Fault-injection MCP tests cover failure before a write, a lost response after a successful commit, SQLite contention and non-retryable errors. The original save format, operating-policy text, commands and legacy aliases are preserved.

```sh
npx --yes --package=https://github.com/KinsonLai/chatquest-ai/releases/download/v0.3.1/chatquest-ai-0.3.1.tgz chatquest
```

Restart the server and refresh ChatGPT's connector metadata to load the new server instructions. Existing v0.3.0 processes remain on the old handler until upgraded. The engine and SDK tests do not establish automatic recovery inside a ChatGPT product conversation.
